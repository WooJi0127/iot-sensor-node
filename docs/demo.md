# 60–90 秒演示

1. **0–15 秒**：仓库根目录运行 `python run.py`，说明使用软件模拟、无必需外部依赖。
2. **15–35 秒**：打开 localhost:8000，指出三个节点、单位与不同颜色/线型，切换温度/湿度/光照。异常标签随机出现，不保证演示时间内出现。
3. **35–50 秒**：打开 `/latest`，展示 Unix 毫秒、三个指标和布尔型标签，说明异常检测项目可直接轮询此接口。
4. **50–65 秒**：点击“导出历史 CSV”，展示节点、时间和指标；说明内存仅保留每节点 600 帧，重启清空。
5. **65–90 秒**：展示完整测试结果，以及 C 主机程序 `--frames 3` 的有限 JSON 输出。说明软件/协议测试已做，真实 STM32、ESP-AT、MQTT 尚未验证。

如需稳定展示异常数据，先在 Python 中注入固定随机发生器与时间并离线查看结果，不能把临时人工改值称为真实设备告警。不要在演示中等待概率事件。

## 常见面试问题

**SSE 为什么不能写 Content-Length: 0？** 它宣告响应没有正文，标准客户端可能立即结束读取。这里使用关闭连接定界并保持事件流持续输出。

**慢客户端怎么办？** 每客户端 32 个待发事件，满时丢最早事件，采样不执行网络写入；socket 写入超时和 finally 清理连接。代价是可能丢帧，不满足可靠消息投递。

**随机种子为什么不保证两次实时输出相同？** 读数还依赖输入时间和调用顺序。复现必须固定这两者，实时模式有意使用当前 Unix 时间。

**为什么使用内存历史？** 避免把数据库作为演示前提，容量和生命周期容易说明；代价是不能长期存档或断电恢复。

**重复时间戳为什么忽略？** 初始快照与 SSE 重连可能重复；严格按节点递增避免曲线增加假样本。时钟回拨会导致数据损失，真实设备需明确时钟同步策略。

**真实硬件还缺什么？** HAL 驱动、ESP-AT 版本确认、UART 响应状态机、设备时钟、板级链接/初始化和烧录验证。当前 C 主机仅验证序列化与协议。
